## 1. Контекст и проблемы

### 1.1. Текущее состояние

Бэкенд SRP (Service for Regulations and Policies) генерирует корпоративные регламенты на русском языке через AI-провайдеров.

**Архитектура на данный момент:**
- Один эндпоинт `POST /api/generate` — синхронная генерация
- Один LLM-запрос = весь документ целиком
- Системный промпт содержит все требования (10 правил) + эталонный пример
- `max_tokens = 32768`, `timeout = 900` секунд
- Провайдеры: Groq (недоступен), Ollama qwen2.5:7b (работает), YandexGPT (не настроен)
- Реально работающий провайдер — только **Ollama с qwen2.5:7b**

### 1.2. Выявленные проблемы

| № | Проблема | Корень |
|---|----------|--------|
| 1 | **Модель «выдыхается»** к середине документа | qwen2.5:7b не может поддерживать качество генерации на 20-40К символов |
| 2 | **Пропуск целых этапов** процесса | Однозапросная генерация не охватывает все стадии |
| 3 | **Промпт-хакинг** — модель «забывает» требования из начала промпта | Из-за ограничения контекста qwen2.5:7b (32K токенов) промпт съедает ~3-4K, на выход остаётся ~28K, но качество падает после ~10K |
| 4 | **Невозможность аудита** | Нельзя проверить связность — нет «второго взгляда» LLM на готовый документ |
| 5 | **Привязанность к провайдеру** | Если Groq заработает — текущий промпт не оптимизирован под его возможности |

### 1.3. Ключевое ограничение

Ровно **один работающий провайдер**: Ollama + qwen2.5:7b (context window: 32 768 токенов).

**Что это значит для архитектуры:**
- Каждый LLM-вызов должен укладываться в ~30K токенов (вход + выход)
- Модель не может «запомнить» всё в одном запросе → нужно разделять
- Каждый этап должен быть достаточно простым, чтобы модель не «теряла нить»

## 2. Требования

### 2.1. Функциональные требования

| ID | Требование | Приоритет |
|----|-----------|-----------|
| FR-01 | Регламент должен ПОЛНОСТЬЮ описывать процесс от начала до конца | MUST |
| FR-02 | Каждый шаг: КТО, ЧТО, КАК, В КАКИЕ СРОКИ делает | MUST |
| FR-03 | Конец одного раздела логически связывается с началом следующего | MUST |
| FR-04 | Решение работает для ЛЮБОЙ темы (не только ГСМ) | MUST |
| FR-05 | «Вода» и бессмысленные пункты недопустимы | MUST |
| FR-06 | Раздел видит содержание предыдущих разделов (связность) | SHOULD |
| FR-07 | Система исправляет ошибки связности постфактум (аудит) | SHOULD |
| FR-08 | Пользователь может видеть прогресс генерации | COULD |
| FR-09 | Возможность перегенерировать отдельный раздел | COULD |

### 2.2. Нефункциональные требования

| ID | Требование | Цель |
|----|-----------|------|
| NFR-01 | Время полной генерации | ≤ 15 минут (для 10 разделов) |
| NFR-02 | Работа только на qwen2.5:7b (локально, Ollama) | MUST |
| NFR-03 | Каждый LLM-вызов ≤ 30K токенов (вход + выход) | MUST |
| NFR-04 | Сохранение промежуточных результатов при падении | SHOULD |
| NFR-05 | API обратно совместимо с текущим | MUST |

### 2.3. Принципы проектирования

1. **Каждый этап — минимальная единица работы**, которую модель может выполнить качественно
2. **Контекст каждого этапа фокусирован** — не нагружаем модель избыточными требованиями
3. **Аудит — отдельный этап**, а не чек-лист в промпте
4. **Промпты универсальны** — не привязаны к теме (никаких «ГСМ», «АЗС» и т.д.)

## 3. Архитектура многоэтапной генерации

### 3.1. Общая схема

```
Пользователь                  Backend                        LLM (Ollama qwen2.5:7b)
    │                            │                                   │
    │ POST /api/generate         │                                   │
    │ (topic, provider)          │                                   │
    │ ────────────────────────>  │                                   │
    │                            │                                   │
    │ 202 { generation_id }      │                                   │
    │ <────────────────────────  │                                   │
    │                            │                                   │
    │ [Фоновый процесс]          │                                   │
    │                            │  ┌──────────────────────────┐     │
    │                            │  │  Этап 1: Составление     │     │
    │                            │  │  плана (оглавления)      │     │
    │                            │  │  1 LLM-вызов             │     │
    │                            │  └──────────┬───────────────┘     │
    │                            │             │ 1. prompt (plan)    │
    │                            │             │ ─────────────────>  │
    │                            │             │ <── plan (markdown) │
    │                            │             │                     │
    │                            │  ┌──────────┴───────────────┐     │
    │                            │  │  Этап 2: Аннотации       │     │
    │                            │  │  разделов (краткое       │     │
    │                            │  │  содержание)             │     │
    │                            │  │  1 LLM-вызов             │     │
    │                            │  └──────────┬───────────────┘     │
    │                            │             │ 2. prompt (annots)  │
    │                            │             │ ─────────────────>  │
    │                            │             │ <── annotated plan  │
    │                            │             │                     │
    │                            │  ┌──────────┴───────────────┐     │
    │                            │  │  Этап 3: Поразделная     │     │
    │                            │  │  генерация (N вызовов)   │     │
    │                            │  │  N = 8-15 разделов       │     │
    │                            │  └──────────┬───────────────┘     │
    │                            │             │ 3.i prompt (sect)   │
    │                            │             │ ─────────────────>  │
    │                            │             │ <── section i text  │
    │                            │             │  (повтор N раз)     │
    │                            │             │                     │
    │                            │  ┌──────────┴───────────────┐     │
    │                            │  │  Этап 4: Аудит           │     │
    │                            │  │  связности (2 вызова)    │     │
    │                            │  └──────────┬───────────────┘     │
    │                            │             │ 4a. audit prompt    │
    │                            │             │ ─────────────────>  │
    │                            │             │ <── audit report    │
    │                            │             │ 4b. completeness    │
    │                            │             │ ─────────────────>  │
    │                            │             │ <── gap report      │
    │                            │             │                     │
    │                            │  ┌──────────┴───────────────┐     │
    │                            │  │  Этап 5: Сборка .docx   │     │
    │                            │  │  (без LLM)              │     │
    │                            │  └──────────────────────────┘     │
    │                            │                                   │
    │  [Пользователь polling]    │                                   │
    │ GET /api/generate/{id}/status                                  │
    │ ────────────────────────>  │                                   │
    │ <── { stage: 3, progress: 60% }                               │
    │                            │                                   │
    │ GET /api/documents/{id}/download (после завершения)            │
    │ ────────────────────────>  │                                   │
    │ <── .docx file            │                                   │
```

### 3.2. Этапы в разрезе токенов

| Этап | LLM-вызовы | Вход (tokens) | Выход (tokens) | Ожидаемое время |
|------|-----------|---------------|----------------|-----------------|
| 1. План | 1 | ~150 | ~400 | 5-15 сек |
| 2. Аннотации | 1 | ~600 | ~1000 | 10-30 сек |
| 3. Генерация (1 раздел) | N (8-15) | ~1500-4000 | ~1500-3000 | 30-120 сек × N |
| 4а. Аудит (противоречия) | 1 | ~500 + документ | ~1000 | 30-60 сек |
| 4b. Аудит (полнота) | 1 | ~500 + план | ~1000 | 20-40 сек |
| 4с. Фикс (при необходимости) | ≤3 | ~2000 | ~2000 | 30-60 сек × ≤3 |
| **Итого** | **13-22** | — | — | **~10-30 минут** |

### 3.3. Ключевое решение: последовательная vs параллельная генерация разделов

#### Вариант A: Последовательная (рекомендуется для MVP)

Каждый раздел генерируется по очереди. Раздел N получает:
- План + аннотации ВСЕХ разделов (общий контекст)
- Содержание раздела N-1 (для связки)
- Свою аннотацию (для фокуса)

**Плюсы:**
- Максимальная связность
- Каждый следующий раздел «знает» предыдущий
- Проще отладка

**Минусы:**
- Медленнее (N последовательных вызовов)
- При падении на разделе 8 — потеря прогресса

#### Вариант B: Параллельная

Все разделы генерируются одновременно. Каждый раздел получает только план + аннотации.

**Плюсы:**
- Один round-trip к LLM (группа параллельных запросов)
- Время генерации ~время одного раздела

**Минусы:**
- Разделы не видят друг друга → риск несвязности
- Audit вынужден делать больше работы

**Решение для MVP: Вариант A (последовательный).**
Причина: качество документа важнее скорости. Параллельный вариант — оптимизация Stage 5+.

### 3.4. Фоновый процесс и polling

Текущая архитектура синхронная (пользователь ждёт ответ). Для multi-stage это неприемлемо (10-30 минут).

**Решение:**
- `POST /api/generate` возвращает `202 Accepted` + `generation_id`
- Запускается **background task** (asyncio Task)
- Пользователь опрашивает `GET /api/generate/{generation_id}/status`
- После завершения: `GET /api/documents/{doc_id}/download`

**Поток:**
```
1. POST /api/generate → 202 { generation_id: "uuid", status: "accepted" }
2. Background task: Stage 1 → Stage 2 → Stage 3 → Stage 4 → Stage 5
3. В процессе: обновляется status/progress в таблице generation_sessions
4. После завершения: создаётся запись в documents, docx_path, status = "completed"
5. GET /api/generate/{id}/status → { status: "generating", stage: 3, progress: 60 }
6. GET /api/generate/{id}/status → { status: "completed", document_id: "...", filename: "..." }
7. GET /api/documents/{doc_id}/download → .docx файл
```

## 4. Описание этапов

### 4.1. Этап 1: Составление плана (оглавления)

**Цель:** LLM генерирует иерархическое оглавление будущего регламента.

**Вход:** Тема регламента (topic)
**Выход:** Список разделов с иерархией (максимум 3 уровня вложенности)

**Логика:**
```
1. Вызвать LLM с промптом Stage 1
2. Распарсить ответ:
   - Разделы 1-го уровня (##) → основные разделы
   - Подразделы (###) → подразделы
   - Собрать в структурированный JSON:
     [
       {"number": 1, "title": "...", "children": [
         {"number": 1.1, "title": "...", "children": []}
       ]},
       ...
     ]
3. Сохранить план в generation_plan (JSON)
4. Обновить статус сессии
```

**Ограничение:** Минимум 6 разделов, максимум 15. Если LLM вернул меньше 6 — повтор с более строгим промптом (макс. 1 повтор).

**Fail-overs:**
- Если парсинг ответа не удался → повтор (макс. 2 попытки)
- Если после 2 попыток план не получен → сессия в статус `failed`

### 4.2. Этап 2: Аннотации разделов

**Цель:** Для каждого раздела LLM пишет краткое содержание (3-5 предложений), указывая:
- Какие должности участвуют
- Какие ИТ-системы задействованы
- Какие документы создаются
- Какие ключевые шаги описываются
- Какие сроки/нормативы применяются

**Вход:** План (оглавление) из Этапа 1
**Выход:** Тот же план, но с полем `annotation` для каждого раздела

**Логика:**
```
1. Вызвать LLM с промптом Stage 2 (план в контексте)
2. Распарсить ответ — получить аннотации для каждого раздела
3. Обновить generation_plan (добавить annotation к каждому разделу)
4. Обновить статус сессии
```

**Зачем нужен этот этап?**
- Аннотации — «единая карта» документа для всех последующих этапов
- Каждый раздел «знает» что будет в других разделах → меньше противоречий
- Раздел 3 может ссылаться на документ, который будет создан в разделе 5

### 4.3. Этап 3: Поразделная генерация (последовательная)

**Цель:** Написать каждый раздел регламента полно и детально.

**Вход для раздела N:**
- План + аннотации (все разделы)
- Текст раздела N-1 (или последние 2 абзаца)
- Аннотация раздела N

**Выход:** Полный текст раздела N в markdown

**Логика:**
```
Для i = 1 to N:
  1. Собрать контекст:
     - План + аннотации всех разделов
     - Текст раздела i-1 (если i > 1)
     - Аннотация раздела i
  2. Сформировать промпт Stage 3
  3. Вызвать LLM
  4. Сохранить content раздела i в document_sections
  5. Обновить прогресс
  6. Если ошибка:
     - Повторить (макс. 1 раз)
     - Если снова ошибка → раздел status = "failed", продолжить со следующим
```

**Формат хранения:** Каждый раздел сохраняется как отдельная запись в `document_sections`:
- `section_number` — порядковый номер
- `title` — название раздела
- `content` — полный markdown-текст
- `annotation` — аннотация из Этапа 2
- `status` — completed / failed / needs_fix
- `fix_attempts` — количество перегенераций

**Правила форматирования внутри раздела:**
- Активный залог: [Должность] выполняет [Действие] в [Срок] через [ИТ-система]
- Конкретные сроки (3 дня, 2 часа, не позднее 12:00)
- Сквозная нумерация пунктов 1.1, 1.2, ...
- Ссылки на приложения (Приложение N)
- Условная логика: Если [условие] → [действие 1], иначе → [действие 2]

### 4.4. Этап 4: Аудит связности

**(Подробно описан в разделе 8)**

Кратко:
1. **4а — Аудит противоречий:** LLM читает полный документ и проверяет терминологию, повторяемость, логику
2. **4b — Аудит полноты:** LLM сверяет документ с планом — все ли этапы описаны
3. **4c — Исправление (если нужно):** Перегенерация проблемных разделов с аудит-отчётом в контексте

### 4.5. Этап 5: Сборка .docx

**Цель:** Склеить все разделы в единый .docx файл.

**Логика:**
```
1. Собрать все разделы из document_sections в порядке section_number
2. Соединить разделы через разделитель-перенос
3. Проверить что документ не пустой
4. Передать в существующий docx_builder.build_docx()
5. Сохранить .docx в generated/
6. Создать запись в documents (со ссылкой на сессию)
7. Обновить статус сессии → "completed"
```

## 5. Модели данных

### 5.1. Новая таблица: `generation_sessions`

```sql
CREATE TABLE IF NOT EXISTS generation_sessions (
    id              TEXT PRIMARY KEY,           -- UUID v4
    topic           TEXT NOT NULL,              -- Тема регламента
    status          TEXT NOT NULL DEFAULT 'accepted'
                    CHECK(status IN (
                        'accepted',             -- Принят, ожидает начала
                        'planning',             -- Этап 1: генерация плана
                        'annotating',           -- Этап 2: генерация аннотаций
                        'generating',           -- Этап 3: генерация разделов
                        'auditing',             -- Этап 4: аудит связности
                        'assembling',           -- Этап 5: сборка .docx
                        'completed',            -- Готов
                        'failed'                -- Ошибка
                    )),
    current_stage   TEXT NOT NULL DEFAULT 'accepted',  -- Текущий этап (дублирует status для query)
    stage_progress  INTEGER DEFAULT 0,          -- Прогресс этапа (0-100%)
    total_sections  INTEGER DEFAULT 0,          -- Общее количество разделов
    completed_sections INTEGER DEFAULT 0,       -- Сколько разделов сгенерировано
    provider_used   TEXT DEFAULT '',             -- Какой провайдер выбран
    document_id     TEXT,                        -- FK → documents.id (после завершения)
    error_message   TEXT,                        -- Текст ошибки при status='failed'
    created_at      TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at      TEXT NOT NULL DEFAULT (datetime('now')),
    completed_at    TEXT
);

CREATE INDEX IF NOT EXISTS idx_sessions_status
    ON generation_sessions(status);
CREATE INDEX IF NOT EXISTS idx_sessions_created_at
    ON generation_sessions(created_at DESC);
```

### 5.2. Новая таблица: `generation_plans`

```sql
CREATE TABLE IF NOT EXISTS generation_plans (
    id              TEXT PRIMARY KEY,           -- UUID v4
    session_id      TEXT NOT NULL REFERENCES generation_sessions(id),
    plan_json       TEXT NOT NULL,              -- JSON-массив разделов с полями:
                                               --   number, title, level, children[], annotation
    raw_plan        TEXT NOT NULL,              -- Сырой ответ LLM (markdown)
    raw_annotations TEXT,                       -- Сырой ответ LLM с аннотациями (markdown)
    created_at      TEXT NOT NULL DEFAULT (datetime('now')),
    UNIQUE(session_id)
);
```

**Формат plan_json:**
```json
[
  {
    "number": 1,
    "title": "Общие положения",
    "level": 1,
    "annotation": "В разделе описываются цели и область применения регламента...",
    "children": [
      {
        "number": 1.1,
        "title": "Цель документа",
        "level": 2,
        "annotation": "...",
        "children": []
      }
    ]
  },
  {
    "number": 2,
    "title": "Термины и определения",
    "level": 1,
    "annotation": "...",
    "children": []
  }
]
```

### 5.3. Новая таблица: `document_sections`

```sql
CREATE TABLE IF NOT EXISTS document_sections (
    id              TEXT PRIMARY KEY,           -- UUID v4
    session_id      TEXT NOT NULL REFERENCES generation_sessions(id),
    section_number  INTEGER NOT NULL,           -- Порядковый номер (1, 2, 3...)
    title           TEXT NOT NULL,              -- Название раздела
    level           INTEGER NOT NULL DEFAULT 1, -- Уровень вложенности (1, 2, 3)
    annotation      TEXT DEFAULT '',             -- Аннотация из Этапа 2
    content         TEXT DEFAULT '',             -- Сгенерированный markdown-текст
    status          TEXT NOT NULL DEFAULT 'pending'
                    CHECK(status IN (
                        'pending',              -- Ожидает генерации
                        'generating',           -- Генерируется
                        'completed',            -- Готов
                        'failed',               -- Ошибка генерации
                        'needs_fix'             -- Требуется исправление (после аудита)
                    )),
    fix_attempts    INTEGER NOT NULL DEFAULT 0, -- Количество попыток исправления
    audit_issues    TEXT DEFAULT '',             -- JSON: список проблем из аудита для этого раздела
    created_at      TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at      TEXT NOT NULL DEFAULT (datetime('now')),
    UNIQUE(session_id, section_number)
);

CREATE INDEX IF NOT EXISTS idx_sections_session
    ON document_sections(session_id, section_number);
```

## 6. API контракты

### 6.1. Новый эндпоинт: POST /api/generate (изменённый)

**Request** — без изменений (обратная совместимость):
```json
{
  "topic": "Регламент по учёту ГСМ на АЗС",
  "provider": "auto"
}
```

**Успешный ответ (202 Accepted)** — ИЗМЕНЁН (был 201):
```json
{
  "generation_id": "uuid-string",
  "status": "accepted",
  "estimated_seconds": 600
}
```

> **Важно:** Если провайдер выбран явно (не `auto`) и недоступен → 400 с сообщением.

**Поля ответа:**

| Поле | Тип | Описание |
|------|-----|----------|
| `generation_id` | UUIDv4 | ID сессии генерации |
| `status` | string | `"accepted"` — принято в обработку |
| `estimated_seconds` | int | Примерное время ожидания (оценка) |

**HTTP-статусы:**
| Код | Ситуация |
|-----|----------|
| 202 | Запрос принят, генерация запущена |
| 422 | Валидационная ошибка (тема пустая/длинная, неверный провайдер) |
| 503 | Все провайдеры недоступны |

### 6.2. Новый эндпоинт: GET /api/generate/{generation_id}/status

**Request:**
```
GET /api/generate/a1b2c3d4-.../status
```

**Успешный ответ (200 OK):**

```json
{
  "generation_id": "a1b2c3d4-...",
  "status": "generating",
  "stage": 3,
  "stage_name": "Генерация раздела 5/10",
  "progress": 45,
  "estimated_remaining_seconds": 300,
  "error_message": null,
  "document_id": null
}
```

**Поля ответа:**

| Поле | Тип | Описание |
|------|-----|----------|
| `generation_id` | string | ID сессии |
| `status` | string | `"accepted"` / `"generating"` / `"completed"` / `"failed"` |
| `stage` | int (1-5) | Номер текущего этапа |
| `stage_name` | string | Человекочитаемое название этапа |
| `progress` | int | Общий прогресс (0-100%) |
| `estimated_remaining_seconds` | int | Примерное время до завершения |
| `error_message` | string/null | Ошибка (если status=failed) |
| `document_id` | string/null | ID документа (только при status=completed) |

**HTTP-статусы:**
| Код | Ситуация |
|-----|----------|
| 200 | OK (статус получен) |
| 404 | Сессия с таким ID не найдена |

### 6.4. Схема статусов сессии

```
accepted → planning → annotating → generating → auditing → assembling → completed
                                                              ↓
                                                           failed
```

**Возврат из failed:**
- Если сессия в `failed`, можно вызвать `POST /api/generate` заново
- Сессия остаётся в БД для анализа


### 8.2. Типы проблем и стратегии исправления

| Тип | Пример | Стратегия исправления | Код |
|-----|--------|-----------------------|-----|
| **Терминология** | "Гл. инженер" vs "Главный инженер" | Авто-замена через regex (BE-side) | AUTO_FIX |
| **Логика** | Раздел 3: срок 3 дня, Раздел 5: срок 5 дней | Перегенерация раздела с контекстом | REGENERATE |
| **Связность** | Раздел заканчивается, непонятно что дальше | Перегенерация с акцентом на связку | REGENERATE |
| **Полнота** | Раздел описан поверхностно (<5 шагов) | Перегенерация с требованием детализации | REGENERATE |
| **Пропуск** | Этап не описан совсем | Создание нового раздела | NEW_SECTION |

### 8.3. Логика аудита (псевдокод)

```python
async def run_audit(session_id: str, full_document: str, plan: dict):
    # Этап 4a: Аудит противоречий
    audit_report = await llm.generate(
        prompt=build_audit_contradiction_prompt(full_document),
        system_prompt=AUDIT_SYSTEM_PROMPT,
        max_tokens=2048,
    )
    contradictions = parse_json_from_llm_response(audit_report)
    
    # Этап 4b: Аудит полноты
    completeness_report = await llm.generate(
        prompt=build_audit_completeness_prompt(plan, full_document),
        system_prompt=COMPLETENESS_SYSTEM_PROMPT,
        max_tokens=2048,
    )
    gaps = parse_json_from_llm_response(completeness_report)
    
    # Сохраняем отчёт в сессию
    save_audit_report(session_id, contradictions, gaps)
    
    # Определяем, какие разделы требуют исправления
    sections_to_fix = identify_sections_to_fix(contradictions, gaps)
    
    # Этап 4c: Исправление проблемных разделов
    for section in sections_to_fix:
        regenerate_section(session_id, section, audit_context=...)
    
    # Если были исправления — повторяем аудит для исправленных разделов
    if sections_to_fix:
        await run_audit(session_id, get_updated_document(session_id), plan)
```

### 8.4. Защита от зацикливания

- Максимум **2 полных цикла аудит-исправление** на сессию
- Максимум **2 попытки исправления** на один раздел
- Если после 2 попыток раздел всё ещё с проблемами — фиксируется в `audit_issues` и пропускается

### 9.4. Схема нового `multi_stage_generator.py`

```python
class MultiStageGenerator:
    """Оркестратор многоэтапной генерации регламента."""
    
    def __init__(self, provider: BaseLLMProvider, db: Session):
        self.provider = provider
        self.db = db
    
    async def run(self, session: GenerationSession, topic: str):
        try:
            # Этап 1: План
            await self._update_status(session, "planning", 0)
            plan = await Stage1Planner(self.provider).generate(topic)
            save_plan(session, plan)
            
            # Этап 2: Аннотации
            await self._update_status(session, "annotating", 20)
            annotations = await Stage2Annotator(self.provider).generate(plan, topic)
            save_annotations(session, annotations)
            
            # Этап 3: Разделы
            await self._update_status(session, "generating", 40)
            sections = plan["sections"]
            for i, section in enumerate(sections):
                prev_content = get_previous_section_content(session, i)
                content = await Stage3Writer(self.provider).generate(
                    section=section,
                    plan=plan,
                    previous_section_content=prev_content,
                )
                save_section(session, i, content)
                progress = 40 + (i + 1) * 40 // len(sections)
                await self._update_progress(session, progress)
            
            # Этап 4: Аудит
            await self._update_status(session, "auditing", 80)
            full_doc = assemble_full_document(session)
            await Stage4Auditor(self.provider).run(session, full_doc, plan)
            
            # Этап 5: Сборка
            await self._update_status(session, "assembling", 95)
            docx_path = await Stage5Assembler().run(session)
            finalize_document(session, docx_path)
            
        except Exception as e:
            await self._mark_failed(session, str(e))
```

### 9.5. Интеграция с существующим `generator.py`

**Решение:** НЕ заменять существующий `generator.py`, а добавить новый путь:

```
Пользовательский запрос
    │
    ├── provider = "generation" / "auto" (multi-stage)
    │       → MultiStageGenerator
    │
    └── provider = "groq" / "ollama" / "yandexgpt" (legacy single-stage)

```

**ProviderEnum** расширяется значением `"generation"`:
```python
class ProviderEnum(str, Enum):

    groq = "groq"
    yandexgpt = "yandexgpt"
    ollama = "ollama"
    generation = "generation"  # NEW: multi-stage generation
```

При `provider = "generation"` или `provider = "auto"` (если включено по умолчанию):
1. Всегда использует Ollama (единственный рабочий провайдер)
2. Запускает MultiStageGenerator в фоне

## 11. Edge Cases

| Ситуация | Ожидаемое поведение |
|----------|--------------------|
| **LLM вернул непарсибельный план** (не JSON) | Повтор запроса (макс. 2). Если не удалось → сессия failed |
| **LLM вернул меньше 6 разделов** | Повтор с более строгим промптом «Разделов должно быть минимум 6» |
| **LLM вернул больше 15 разделов** | Взять первые 15 |
| **Один раздел не сгенерировался** (failed) | Продолжить со следующим. В audit отметить как missing |
| **Все разделы failed** (провайдер упал) | Сессия → failed. Пользователь → status + ошибка |
| **Пользователь закрыл браузер** | Фоновая генерация продолжается. Документ доступен по ID |
| **Перезапуск backend во время генерации** | Сессия остаётся в БД со статусом, в котором была прервана. При перезапуске можно возобновить (опционально) |
| **Два запроса от одного пользователя** | Каждый получает свой generation_id. Генерации независимы |
| **Тема содержит спецсимволы / SQL-инъекции** | Pydantic валидация, parameterized queries SQLAlchemy |
| **Тема более 2000 символов** | 422 Validation Error (как сейчас) |
| **Тема на английском** | Генерируется на русском (промпт на русском). Качество может быть ниже |
| **Модель выдает бессмысленный текст в разделе** | Audit (4a) выявит проблему → регенерация раздела |
| **Зацикливание исправлений** | max 2 цикла audit → защита |

## Приложение B: Словарь терминов

| Термин | Определение |
|--------|------------|
| **Multi-stage generation** | Многоэтапная генерация — разбиение одной задачи на несколько последовательных LLM-вызовов |
| **Session** | Сессия генерации — совокупность всех этапов для одного регламента |
| **Stage** | Этап — один логический шаг в цепочке генерации |
| **Plan** | Оглавление регламента, созданное на Этапе 1 |
| **Annotation** | Краткое содержание раздела (3-5 предложений), созданное на Этапе 2 |
| **Audit** | Проверка связности, полноты и терминологии готового документа |
| **Fix pass** | Перегенерация раздела с учётом замечаний аудита |
| **Background task** | Фоновая задача (asyncio Task), выполняющая генерацию без блокировки API |
| **Polling** | Механизм опроса статуса генерации клиентом |

## Приложение C: Чек-лист для QA-верификации

При проверке реализации multi-stage generator QA должен:

1. **POST /api/generate с `provider: "generation"`:**
   - [ ] Ответ 202 с `generation_id`
   - [ ] В БД появилась запись в `generation_sessions`

2. **GET /api/generate/{id}/status:**
   - [ ] Возвращает корректный `status` и `stage`
   - [ ] `progress` увеличивается с течением времени
   - [ ] После завершения: `status: "completed"`, есть `document_id`

3. **Содержание этапов:**
   - [ ] Этап 1: план содержит 6-15 разделов
   - [ ] Этап 2: каждый раздел имеет аннотацию (3+ предложений)
   - [ ] Этап 3: каждый раздел содержит 8+ пунктов с должностями и сроками
   - [ ] Этап 4: аудит отчёт в JSON
   - [ ] Этап 5: .docx создан и открывается

4. **Обратная совместимость:**
   - [ ] `POST /api/generate` с `provider: "ollama"` работает синхронно (как раньше)
   - [ ] `GET /api/documents` показывает все документы (и старые, и новые)

5. **Обработка ошибок:**
   - [ ] При падении LLM — сессия в `failed`
   - [ ] При недоступности провайдера — 503
   - [ ] При пустой теме — 422
