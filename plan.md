# Plan: Service for Regulations and Policies (SRP)

> Версия плана: v2.1
> Дата: 2026-06-20
> Статус: Утверждён (обсуждение с заказчиком завершено)

---

## 1. Product Vision

Сервис для создания, управления и генерации корпоративных регламентов и политик для холдингов.

**Ключевая идея:** сервис анализирует существующие документы компании, строит базу знаний (граф связей между документами), понимает стилистику и структуру каждого холдинга, после чего способен генерировать новый регламент «с нуля» или на основе черновиков — с учётом внутренней базы знаний, внешнего законодательства и ГОСТ (опционально).

**Дополнительно:** сервис сам является MCP-сервером, что позволяет другим AI-агентам пользоваться его знаниями и инструментами.

## 4. Core Requirements

### 4.1 Модуль загрузки и анализа документов

- Загрузка документов в форматах **Word (.docx)** и **PDF**
- Парсинг структуры документа: оглавление, разделы, подразделы, таблицы
- Извлечение терминов и определений, сокращений
- Выявление речевых паттернов и стилистических оборотов (для обучения шаблона холдинга)
- Сохранение извлечённой структуры как «профиля документа» в базу знаний

### 4.2 Профили холдингов

- **Наименование холдинга** — обязательное поле, идентификатор
- **ИНН** — опционально на MVP, обязательно в дальнейшем
- **Юридическая принадлежность** — ООО / АО / ПАО / иное
- **Шаблон документа** — структура (какие разделы обязательны, в каком порядке)
- **Стилистика** — типовые обороты, оформление таблиц/списков
- **Галочка «Учитывать ГОСТ Р 7.0.97-2016»** — если включена, сервис проверяет структуру и оформление по ГОСТу
- **Список источников законодательства** — какие источники искать для данного холдинга
- Возможность создать несколько холдингов, у каждого — свои настройки

### 4.3 База знаний и граф связей

- **Семантический граф** связей между документами:
  - Документ А ссылается на документ Б
  - Документ В изменяет/дополняет документ Г
  - Приказ Х частично отменяет раздел документа Y
- При генерации нового документа сервис автоматически находит связанные документы и:
  - Или встраивает их данные (реквизиты, даты, нормы)
  - Или ставит перекрёстную ссылку с указанием ответственного
- **Ручное указание влияющих документов**: пользователь может вручную добавить документы, которые влияют на текущий регламент (для специфических случаев, которые система не может определить автоматически)

### 4.4 Генератор документов

- **Входные данные:**
  - Контекстное описание (что должен регулировать документ)
  - Черновики / наработки (загрузка Word/PDF)
  - Вручную указанные влияющие документы (см. п.4.3)
- **Учитываемые данные:**
  - Профиль холдинга (шаблон, стилистика, ГОСТ)
  - Внутренняя база знаний (связанные документы, термины)
  - Внешнее законодательство (из настроенных источников)
- **Выходные данные:** полноценный Word-документ (.docx) с:
  - Названием и оглавлением
  - Разделами в соответствии с шаблоном холдинга
  - Списком внутренних документов (таблица ссылок)
  - Списком внешних документов (законодательство)
  - Терминами и определениями
  - Сокращениями
  - Нумерацией, колонтитулами (если предусмотрено шаблоном)

### 4.5 Модуль внешнего законодательства

- **Архитектура плагинов:** каждый источник — это адаптер с единым интерфейсом `Поиск(Запрос) → [Результаты]`
- **Встроенные источники для MVP:**
  - pravo.gov.ru — официальный портал правовой информации
  - docs.cntd.ru — Техэксперт (ограниченно бесплатный)
- **Платные источники (заглушка на MVP):**
  - Консультант+ (галочка в настройках)
  - Гарант (галочка в настройках)
- **Конструктор источников:** пользователь может добавить свой источник (URL, формат запроса, парсер ответа)
- Поиск производится по ключевым словам из контекста документа

### 4.6 Модуль внутренних приказов

- Загрузка приказов (Word/PDF)
- Сервис анализирует: «Какой документ этот приказ изменяет/дополняет/отменяет»
- Приказ привязывается к регламенту как **изменяющий документ**
- При генерации регламента сервис учитывает все приказы, вносящие изменения
- Версионность: приказ порождает новую версию регламента

### 4.7 Реестр документов и версионность

- **Реестр:** таблица всех документов холдинга
- **Статусы документов:**
  - Черновик (Draft)
  - На согласовании (Review)
  - Утверждён (Approved)
  - Архивирован (Archived)
- **Версионность:**
  - Каждый документ имеет историю версий
  - Новая версия создаётся при:
    - Внесении замечаний пользователем
    - Изменении связанного документа/приказа
    - Ручном создании черновика
  - Старая версия сохраняется (полный доступ для чтения)
  - Сравнение версий (diff) — в перспективе

### 4.8 MCP-сервер

- Сервис является MCP-сервером, реализующим следующие инструменты:
  - `get_holding_profile` — получить профиль холдинга
  - `search_documents` — поиск документов в реестре
  - `get_document_relationships` — граф связей документа
  - `get_terms_and_definitions` — глоссарий холдинга
  - `generate_draft` — создать проект документа (контекст + черновики → готовый документ)
  - `list_sources` — список источников законодательства
- MCP-сервер работает поверх того же API, что и веб-интерфейс

### 4.9 Пользовательский интерфейс (веб)

- **Страница «Дашборд»** — статистика, последние документы, статусы
- **Страница «Реестр документов»** — фильтры, поиск, статусы, версии
- **Страница «Документ»** — просмотр, версии, карта влияний, редактирование
- **Страница «Генератор»** — контекстное окно + загрузка файлов → запуск генерации
- **Страница «Профиль холдинга»** — настройки шаблона, ГОСТ, источники
- **Страница «Карта влияний»** — отображение связей документа (таблица + позже визуальный граф)

**Технологический стек UI:** React 18+ + Vite + TypeScript + Ant Design 5. OpenAPI-генератор клиента (openapi-typescript-codegen) для типизированного взаимодействия с FastAPI backend.

## 7. User Stories (ключевые)

### Story 1: Загрузка и анализ
> Как бизнес-аналитик, я хочу загрузить утверждённый регламент (Word/PDF), чтобы сервис проанализировал его структуру и пополнил базу знаний холдинга.

### Story 2: Ручное указание влияющих документов
> Как бизнес-аналитик, я хочу вручную добавить документ, который влияет на текущий регламент, чтобы учесть специфику, которую система не может определить автоматически.

### Story 3: Генерация нового регламента
> Как бизнес-аналитик, я хочу описать в контекстном окне суть нового регламента и при необходимости загрузить черновики, чтобы сервис сгенерировал полноценный документ с учётом всех внутренних документов и законодательства.

### Story 4: Учёт приказов
> Как бизнес-аналитик, я хочу загрузить приказ, который вносит изменения в регламент, чтобы сервис создал новую версию документа с учётом этих изменений.

### Story 5: Версионность
> Как бизнес-аналитик, я хочу видеть историю версий документа и иметь возможность вернуться к предыдущей версии.

### Story 6: MCP-доступ
> Как AI-агент, я хочу подключиться к MCP-серверу сервиса, чтобы получать шаблоны документов и генерировать новые регламенты программно.

### Story 7: Внешнее законодательство
> Как бизнес-аналитик, я хочу, чтобы сервис автоматически находил актуальные законодательные акты по теме регламента, чтобы документ соответствовал текущему законодательству.

### Story 8: Регистрация и вход
> Как бизнес-аналитик, я хочу зарегистрироваться по email (с кодом подтверждения) и выбрать холдинг из выпадающего списка, чтобы начать работу с документами моего холдинга.

## 8. Out of Scope (текущая версия)

- Электронная подпись и юридически значимый документооборот
- Мобильное приложение
- Полноценный SSO / интеграция с AD
- On-premise установка (первые этапы — локальный запуск)
- Интеграция с 1С / SAP / ERP-системами
- Визуальный граф влияний (таблица — в MVP, граф — Stage 2)

## 9. Risks and Mitigations

| # | Risk | Impact | Probability | Mitigation |
|---|---|---|---|---|
| R1 | Качество парсинга Word/PDF (разная вёрстка) | High | Medium | Пара комбинаций парсеров + ручная корректировка; начать с Word |
| R2 | LLM-галлюцинации (выдуманные законы, ссылки) | High | Medium | RAG-подход: каждое утверждение должно иметь источник. Промпт с инструкцией «не выдумывать» |
| R3 | Законодательные источники меняют API/формат | Medium | High | Архитектура плагинов: сломался один источник — остальные работают |
| R4 | Разные холдинги — разные шаблоны, сложность | Medium | Medium | Гибкая конфигурация шаблона (YAML/JSON), а не хардкод |
| R5 | GigaChat API станет платным / недоступным | Medium | Low | Архитектура смены LLM: переключение на другую модель — одна настройка |
| R6 | SQLite не выдержит много документов | Low | Medium | Закладываем слой абстракции БД; миграция на PostgreSQL в Stage 3 |

## 10. Assumptions

- У холдингов действительно есть устойчивый паттерн оформления документов, который можно выделить
- Пользователь готов загружать примеры «хороших» документов для обучения
- Законодательство РФ доступно через открытые API/сайты
- GigaChat Pro free tier достаточен для MVP-нагрузки
- Локального хранения (SQLite + файлы) хватит на этапе MVP
- Векторное хранилище ChromaDB (встраиваемое) достаточно для MVP

- [ ] Загружен 1+ документ → структура извлечена корректно
- [ ] Создан профиль холдинга → применён при генерации
- [ ] Сгенерирован документ по описанию → открывается в Word, структура соблюдена
- [ ] Автоматически найдены связанные внутренние документы и проставлены ссылки
- [ ] Ручное добавление влияющего документа → учтён при генерации
- [ ] Создана версия 2 документа → версия 1 сохранена и доступна
- [ ] MCP-клиент может вызвать `generate_draft` и получить результат
- [ ] Поиск по pravo.gov.ru выдаёт релевантные законы
