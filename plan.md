## Принципы разработки

1. **Вертикальные срезы** — каждая фаза даёт работающий кусок функциональности (backend + frontend + DB)
2. **LLM-абстракция** — все вызовы LLM через интерфейс `LLMClient`, чтобы легко менять модель
3. **Local-first, cloud-ready** — сначала локальная LLM (Ollama), но архитектура позволяет переключиться на GigaChat / YandexGPT заменой одного класса
4. **Multi-holding с первого дня** — все сущности привязаны к холдингу (holding_id)
5. **Идемпотентность анализа** — повторная установка статуса "approved" не вызывает повторный анализ, если контент не изменился
6. **Никакого MCP Server** — LLM работает напрямую через FastAPI, MCP-сервер избыточен при локальной модели

# Фаза 1: Генерация регламента «с нуля» через локальную LLM

## Objective
Пользователь описывает тему регламента → сервис через локальную LLM генерирует полноценный документ в .docx с заголовком, оглавлением, разделами, и сохраняет его со статусом «черновик».

## Business Value
MVP проверки гипотезы: может ли LLM (Qwen 3.6 36B MoE) генерировать пригодные к использованию корпоративные регламенты. Это самая ценная функция для пользователя.

## Scope

### Backend
1. **LLMClient abstraction:**
   - Базовый класс/интерфейс `LLMClient` с методом `async def generate(prompt: str, **kwargs) -> str`
   - Реализация `OllamaClient` через `httpx` (API: `http://localhost:11434/api/generate`)
   - Поддержка параметров: `temperature=0.3` (низкая температура для юридических текстов), `max_tokens=16384`

2. **PromptBuilder:**
   - Базовый промпт для структуры регламента:
     - Название документа
     - 1. Общие положения
     - 2. Термины и определения
     - 3. Основная часть (зависит от темы)
     - 4. Заключительные положения
     - Перечень нормативных ссылок
   - Системный промпт: "Ты — юрист холдинга, составляешь корпоративные регламенты. Пиши строго, официально, с нумерацией разделов и пунктов."

3. **GeneratorService:**
   - `async def generate_document(topic: str, holding_id: int) -> dict`
   - Формирует промпт → вызывает LLM → получает текст
   - Парсит ответ на разделы (по маркдаун-заголовкам)
   - Собирает .docx через python-docx:
     - Титульная страница: название, дата, статус "Черновик"
     - Оглавление (Table of Contents поле)
     - Разделы с нумерацией 1.1, 1.2, ...
     - Нижний колонтитул: номер страницы
   - Сохраняет файл в `storage/generated/`
   - Создаёт запись в БД (таблица documents)

4. **API Endpoints:**
   - `POST /api/v1/generator/generate` — тело: `{topic: string, holding_id: int}`
     - Ответ: `{document_id, filename, status: "draft", version: 1}`
   - `GET /api/v1/generator/status/{task_id}` — статус генерации
   - `GET /api/v1/documents/{id}/download` — скачать файл

5. **Модель БД:**
   - `Document`: id, holding_id, title, status (draft), file_path, created_at, updated_at

### Frontend
1. **Страница генератора (GeneratorPage):**
   - Текстовое поле (TextArea): описание темы регламента
   - Кнопка «Сгенерировать регламент»
   - Индикация процесса: Steps (Подготовка → Генерация → Оформление)
   - После завершения: сообщение об успехе + кнопка «Скачать» + ссылка на реестр

2. **Страница реестра (DocumentsListPage):**
   - Таблица: ID, Название, Статус (Tag), Дата создания, Действия (Скачать)
   - Фильтры не обязательны на этом этапе
   - Пустое состояние: «Нет документов. Создайте первый через Генератор»

3. **Хедер:**
   - Навигация: Генератор, Документы (простая)
   - Без аутентификации (заглушка)

## Out of Scope
- ❌ Анализ загруженных документов (Фаза 2)
- ❌ Multi-holding (hardcoded holding_id=1)
- ❌ Версионность (Фаза 7)
- ❌ Веб-поиск (Фаза 5)
- ❌ Загрузка черновиков (Фаза 5)
- ❌ Аутентификация (заглушка)
- ❌ Редактирование/удаление документов

## Acceptance Criteria
1. Пользователь вводит «Регламент по обработке персональных данных» → получает .docx
2. В .docx есть: название, оглавление (поле TOC), разделы 1..N, нумерация пунктов, колонтитул
3. Документ отображается в реестре со статусом «Черновик» и версией 1
4. Пользователь может скачать документ из реестра
5. Весь процесс генерации ≤ 5 минут
6. При ошибке (Ollama не отвечает и т.д.) — понятное сообщение, кнопка «Повторить»
7. Документ генерируется на русском языке
8. Промпт не содержит конфеденциальных данных холдинга (не hardcoded)

## Risks
| Риск | Митигация |
|------|-----------|
| Qwen 3.6 36B может быть избыточно медленной для коротких запросов | Использовать non-thinking mode для генерации, thinking mode только для сложного анализа |
| Модель 256K контекста, но генерация может обрываться на длинных документах | Итеративная генерация по разделам при длине >50 стр |
| python-docx не умеет в сложное форматирование | Использовать базовые шаблоны; сложное форматирование позже через библиотеки-надстройки |
| Время генерации > 5 мин при full precision | Использовать Q4_K_M (уже стоит) |
| Python 3.14 несовместимость с httpx или другими библиотеками | Проверить совместимость в Фазе 0; при проблемах — Python 3.12 |

## Assumptions
- Ollama работает на том же хосте (localhost:11434)
- Qwen 3.6 36B MoE понимает русские юридические термины
- .docx — достаточный формат для черновика
- Пользователь не требует идеального форматирования на этом этапе

## Dependencies
- Фаза 0 (окружение)

# Фаза 2: Разбор загруженного документа + Pattern Analysis

## Objective
Пользователь загружает утверждённый регламент (Word/PDF) → система парсит структуру, извлекает термины, определения, сокращения, ссылки и анализирует паттерны оформления холдинга.

## Business Value
Система начинает «понимать» корпоративный стиль документов. Это основа для обучения генерации в Фазе 5.

## Scope

### Backend
1. **ParserService:**
   - `ParserPDF` — извлечение текста из PDF (через PyMuPDF / pdfplumber)
   - `ParserDOCX` — извлечение текста и структуры из .docx (через python-docx)
   - Определение заголовков: по стилям (Heading 1, 2, 3) или по номерам (1., 1.1, и т.д.)
   - Извлечение таблиц из .docx

2. **PatternAnalysisService:**
   - Анализ структуры: какие разделы обязательны, порядок следования
   - Анализ нумерации: формат (1.1, 1.1.1, римские цифры)
   - Анализ терминов: поиск фраз «означает», «понимается», «определяется»
   - Анализ сокращений: поиск паттернов (АББР. / ... (далее — Аббр))
   - Анализ ссылок: на внутренние документы (Регламент №...) и внешние (ФЗ №...)
   - Сохранение паттернов в таблицу `holding_patterns` (JSON-схема структуры)

3. **TermExtractor:**
   - Извлечение терминов с определениями → таблица `document_terms`
   - Извлечение сокращений с расшифровкой → таблица `document_abbreviations`
   - Извлечение ссылок на документы → таблица `document_references`

4. **API Endpoints:**
   - `POST /api/v1/documents/upload` — загрузка файла (multipart)
     - Параметры: file, holding_id, title (опционально)
     - Ответ: document_id, status: "draft"
   - `POST /api/v1/documents/{id}/analyze` — запуск анализа (синхронно для начала)
   - `GET /api/v1/documents/{id}/structure` — получение структуры документа
   - `GET /api/v1/documents/{id}/terms` — термины документа
   - `GET /api/v1/documents/{id}/abbreviations` — сокращения

5. **Модели БД:**
   - `DocumentTerm`: id, document_id, term, definition, created_at
   - `DocumentAbbreviation`: id, document_id, abbreviation, expansion, created_at
   - `DocumentReference`: id, document_id, reference_text, reference_type (internal/external), created_at
   - `HoldingPattern`: id, holding_id, name, pattern_json (JSONSchema структуры), created_at
   - `DocumentSection`: id, document_id, title, level, order, content

### Frontend
1. **Страница загрузки (DocumentUploadPage):**
   - Drag-and-drop зона для .docx, .pdf
   - Поле названия (если не заполнено — из файла)
   - Кнопка «Загрузить и проанализировать»
   - Прогресс анализа

2. **Детальная страница документа (DocumentDetailPage):**
   - Вкладки: Информация / Структура / Термины / Сокращения / Ссылки
   - Структура: Tree-вид (слева заголовки, справа содержимое раздела)
   - Термины: таблица (Термин → Определение)
   - Сокращения: таблица (Сокр. → Расшифровка)

## Out of Scope
- ❌ Генерация с учётом анализа (Фаза 5)
- ❌ Автоматический анализ при смене статуса (Фаза 4)
- ❌ Версионность
- ❌ Веб-поиск
- ❌ Анализ приказов (Фаза 5)

## Acceptance Criteria
1. Пользователь загружает .docx → system извлекает заголовки, термины, сокращения
2. Пользователь загружает .pdf → то же самое
3. Структура отображается в виде дерева (раздел → подраздел → пункт)
4. Термины и сокращения отображаются в таблицах
5. Ссылки на внешние и внутренние документы идентифицированы
6. Паттерны холдинга сохранены (структура, нумерация, формулировки)
7. Все данные привязаны к holding_id

## Risks
| Риск | Митигация |
|------|-----------|
| PDF с отсканированными страницами (не текст, а картинка) | Добавить OCR (Tesseract) как опцию; иначе ручное создание |
| Форматирование .docx нестандартное (не используются стили) | Эвристический парсинг: поиск номеров разделов в тексте |
| Терминология специфичная для отрасли — не все извлекается | Возможность ручного добавления терминов через UI |

## Dependencies
- Фаза 1 (базовый backend + frontend)

# Фаза 3: Документооборот (статусы, Multi-holding, права)

## Objective
Полноценное управление документами с разделением по холдингам, статусной моделью и базовыми правами доступа.

## Business Value
Без этой фазы сервис — просто генератор. Статусы, холдинги и права — основа реального документооборота.

## Scope

### Backend
1. **Статусная модель:**
   - Статусы: `draft` → `review` (на рассмотрении) → `approved` (утверждён) → `cancelled` (отменён) / `archived` (архивный)
   - Полная матрица переходов:
     - `draft` → `review`, `archived`
     - `review` → `draft`, `approved`, `archived`
     - `approved` → `cancelled`, `archived`
     - `cancelled` → `draft`, `archived`
     - `archived` → терминальный (только удаление)
   - Администратор (admin) может перевести документ в любой статус вне зависимости от матрицы
   - Таблица `document_status_history`: id, document_id, status, changed_by, changed_at, comment

2. **Multi-holding:**
   - Таблица `Holding`: id, name, inn, legal_form, created_at
   - Все документы привязаны к holding_id
   - `HoldingPattern` обновлён: уникальность по holding_id + name
   - API: CRUD для холдингов (только admin)

3. **Права доступа:**
   - Таблица `User`: id, email, password_hash, role (admin / editor / member / viewer)
   - Роли в рамках холдинга:
     - `admin` — полный доступ, включая управление пользователями и обход ограничений статусов
     - `editor` — создание, редактирование, смена статусов (с ограничениями матрицы)
     - `member` — (legacy) то же, что editor, отображается как «Редактор»
     - `viewer` — чтение и скачивание, без права изменения
   - JWT-аутентификация
   - Middleware: проверка роли и привязки к холдингу

4. **API Endpoints:**
   - `POST /api/v1/auth/register` — регистрация
   - `POST /api/v1/auth/login` — логин (JWT)
   - `GET /api/v1/auth/me` — текущий пользователь
   - `POST /api/v1/documents/{id}/status` — смена статуса (тело: `{status, comment}`)
   - `GET /api/v1/documents/{id}/history` — история статусов
   - `POST /api/v1/holdings` — создать холдинг (admin)
   - `GET /api/v1/holdings` — список холдингов
   - `PUT /api/v1/holdings/{id}` — обновить холдинг
   - `DELETE /api/v1/holdings/{id}` — удалить холдинг (admin)

### Frontend
1. **Страницы аутентификации:**
   - LoginPage, RegisterPage (с валидацией)
   - Сохранение JWT в localStorage
   - ProtectedRoute, AdminRoute guards

2. **Header:**
   - Показывает: название холдинга, email пользователя, роль
   - Кнопка «Выйти»
   - Навигация в зависимости от роли

3. **Документы:**
   - Возможность смены статуса через select на детальной странице
   - История статусов (Timeline/Ant Design Steps)
   - Цвета статусов: draft(серый), review(оранжевый), approved(зелёный), cancelled(красный), archived(серебро)

4. **Профиль:**
   - Выбор текущего холдинга
   - Смена пароля

## Out of Scope
- ❌ Автоматический анализ при утверждении (Фаза 4)
- ❌ Версионность
- ✅ Управление пользователями (админка) — реализовано:
  - Inline смена роли в таблице пользователей
  - Памятка прав ролей (ROLE_INFO)
  - Создание, редактирование, блокировка/разблокировка, удаление пользователей

## Acceptance Criteria
1. Пользователь может зарегистрироваться и войти
2. Пользователь может создать/выбрать холдинг
3. Пользователь может изменить статус документа (draft → review → approved)
4. История смены статусов сохраняется и отображается
5. Viewer не может изменить статус
6. Admin может создавать холдинги
7. Администратор может перевести документ в любой статус (обход матрицы переходов)
8. Администратор может менять роли пользователей через админ-панель
9. Документы изолированы по холдингам (пользователь видит только свои)

- Фаза 2 (загрузка и анализ) — опционально, можно параллельно

# Фаза 4: Анализ при статусе «Утверждён»

## Objective
При установке статуса `approved` система автоматически запускает pipeline анализа документа и обновляет базу знаний холдинга. Защита от повторного анализа.

## Business Value
Автоматизация наполнения базы знаний: каждый утверждённый документ автоматически учит систему.

## Scope

### Backend
1. **Pipeline анализа (асинхронный):**
   - Триггер: событие смены статуса на `approved`
   - Определение изменений: сравнение hash файла с последним проанализированным
   - Если hash совпадает → анализ не запускается (idempotency)
   - Если hash отличается → полный pipeline:
     1. Extract text
     2. Parse structure (заголовки, разделы)
     3. Extract terms → `document_terms`
     4. Extract abbreviations → `document_abbreviations`
     5. Extract references → `document_references`
     6. Pattern analysis → обновление `holding_patterns`
     7. Embedding: разбивка на chunks → ChromaDB (с метаданными: holding_id, document_id, section)
     8. Mark analysis complete

2. **Таблица анализов:**
   - `DocumentAnalysis`: id, document_id, version_id, file_hash, status (running/complete/error), result_summary, created_at

3. **ChromaDB integration:**
   - Создание коллекции `holding_{id}_documents`
   - Chunk размер: ~1000 токенов с overlap 200
   - Метаданные: holding_id, document_id, section_title, chunk_index
   - Embedding модель: nomic-embed-text (уже установлена)

4. **API Endpoints:**
   - `GET /api/v1/documents/{id}/analyses` — история анализов
   - `GET /api/v1/analysis/pipeline/{analysis_id}` — статус pipeline
   - `POST /api/v1/analysis/reanalyze/{id}` — принудительный перезапуск анализа

### Frontend
1. **Строка процесса анализа:**
   - На детальной странице: отображение pipeline анализа (шаги с иконками)
   - Статусы каждого шага: waiting → running → done/error
   - Общее время анализа

2. **Управление:**
   - Индикация на документе: проанализирован / не проанализирован
   - Кнопка «Перезапустить анализ» (для админов)

## Acceptance Criteria
1. При смене статуса на `approved` запускается анализ
2. Если контент не менялся, а статус снова `approved` — повторного анализа нет
3. Если контент изменился (новая версия) — анализ перезапускается
4. История анализов отображается (когда был, что нашли, статус)
5. Векторная БД (ChromaDB) пополняется новыми эмбеддингами
6. Pipeline устойчив к ошибкам (если один шаг упал, остальные продолжаются)

## Risks
| Риск | Вероятность | Митигация |
|------|------------|-----------|
| ChromaDB нестабильна на Windows | Низкая | Fallback на FAISS в памяти |
| Анализ большого документа (>100 стр) занимает >10 минут | Средняя | Асинхронный pipeline; уведомление пользователя о завершении |
| File hash не меняется, но пользователь хочет переанализировать | Низкая | Кнопка «Принудительный анализ» |

## Dependencies
- Фаза 2 (парсеры и извлечение)
- Фаза 3 (статусная модель)

# Фаза 5: Генерация с учётом базы знаний (RAG + стиль холдинга)

## Objective
Генератор использует проанализированные документы холдинга (из Фаз 2+4) для создания новых документов в корпоративном стиле, с правильными терминами, ссылками на законодательство и внутренние документы.

## Business Value
Ключевое конкурентное преимущество: система пишет не «просто текст», а документ, который выглядит и звучит как документы именно этого холдинга.

## Scope

### Backend
1. **RAG-enhanced GeneratorService:**
   - При получении темы:
     a. Поиск похожих документов в ChromaDB коллекции холдинга (top-k=5)
     b. Извлечение структуры из `holding_patterns` для типа документа
     c. Формирование enriched prompt с примерами
   - Генерация с учётом:
     - Структуры (разделы, порядок)
     - Терминологии (использовать термины из базы)
     - Ссылок на внутренние документы
     - Ссылок на законодательство (поиск в таблице references)

2. **WebSearchService (опционально):**
   - Поиск актуального законодательства по теме
   - Источники: consultant.ru, garant.ru, base.garant.ru
   - Найденные законы → добавление в references документа
   - Реализация: через httpx + парсинг HTML (или через API, если есть доступ)

3. **Загрузка черновиков (Draft Upload):**
   - Пользователь загружает файл-черновик (txt, docx)
   - Система извлекает текст
   - Использует как основу, дополняя и структурируя через LLM

4. **Приказы (Orders):**
   - Загрузка приказов (отдельный тип документа с типом "order")
   - При анализе приказа: поиск фраз «внести изменения в регламент №...», «дополнить пункт ...»
   - Связывание приказа с изменяемым документом
   - Новая модель `DocumentAmendment`: id, order_document_id, amended_document_id, amendment_text

5. **API Endpoints:**
   - `POST /api/v1/generator/generate` — расширенный (с RAG)
     - Новые поля: `upload_draft_ids: int[]`, `influence_document_ids: int[]`
   - `POST /api/v1/documents/upload/order` — загрузка приказа

### Frontend
1. **Генератор (расширенный):**
   - Выбор типа документа (Регламент, Политика, Инструкция, Приказ)
   - Загрузка черновика (опционально)
   - Выбор влияющих документов (мультиселект из реестра)
   - Индикация: «Ищу похожие документы...», «Анализирую законодательство...»

2. **Приказы:**
   - Отдельный фильтр в реестре: тип=Приказ
   - На детальной странице документа: блок «Изменения приказами» — список приказов, которые вносят правки

## Acceptance Criteria
1. Сгенерированный документ содержит термины из базы знаний холдинга
2. Структура документа соответствует паттернам холдинга
3. Документ содержит ссылки на реальные внутренние документы (если есть)
4. Документ содержит ссылки на законодательство (если websearch доступен)
5. Черновик пользователя используется как основа
6. Приказы парсятся и связываются с изменяемыми документами

## Risks
| Риск | Вероятность | Митигация |
|------|------------|-----------|
| RAG возвращает нерелевантные документы | Средняя | Улучшить embedding quality; увеличить k c последующей реранжировкой |
| WebSearch упирается в rate limits / блокировки | Высокая | Кэширование результатов; fallback на ручной ввод ссылок |
| Приказы написаны в свободной форме — сложно парсить | Высокая | Парсить ключевые фразы; ручное подтверждение связей |

## Dependencies
- Фаза 2 (парсинг, термины)
- Фаза 4 (анализ при approved, ChromaDB)
- Фаза 3 (статусная модель)

# Фаза 6: Корректировка по замечаниям пользователя

## Objective
Пользователь вносит правки/замечания к сгенерированному документу → LLM перерабатывает его с учётом замечаний, создавая новую версию.

## Business Value
Редко когда документ принимается с первой попытки. Возможность итеративного улучшения через LLM экономит часы ручного редактирования.

## Scope

### Backend
1. **RevisionService:**
   - Приём замечаний в двух форматах:
     a. Текстовое описание: «Сделай раздел 3 более детальным, добавь про сроки хранения»
     b. Структурированное: привязка к конкретному разделу
   - Формирование промпта: исходный текст + замечание + инструкция «внеси изменения»
   - LLM генерирует исправленный документ
   - Diff: сравнение старой и новой версии (через библиотеку `diff`)

2. **API Endpoints:**
   - `POST /api/v1/documents/{id}/revise` — тело: `{comment: string, target_section?: string}`
     - Ответ: new_version_id, diff_data
   - `GET /api/v1/documents/{id}/versions/{v1}/diff/{v2}` — diff между версиями

### Frontend
1. **Интерфейс правок:**
   - На детальной странице: кнопка «Внести правки»
   - Модальное окно: TextArea для описания замечаний + опциональный выбор раздела
   - Прогресс: «LLM вносит изменения...»

2. **Diff-вьювер:**
   - Использовать `react-diff-viewer-continued` (как в DESIGN.md)
   - Две панели: старая версия (слева, красное) → новая версия (справа, зелёное)
   - Возможность пролистывать

## Acceptance Criteria
1. Пользователь пишет «добавь раздел про ответственность» → система добавляет
2. Пользователь пишет «в разделе 4.2 исправь срок с 5 на 10 дней» → система изменяет
3. Diff между версиями отображается (подсветка изменений)
4. Старая версия сохраняется, новая создаётся (подготовка к версионности)
5. Можно откатиться до предыдущей версии (перезапись или создание новой)

## Risks
| Риск | Вероятность | Митигация |
|------|------------|-----------|
| LLM не точно выполняет замечание (меняет не то, что просили) | Высокая | Промпт с точным цитированием раздела; итеративное уточнение |
| Diff-вьювер путается в больших документах | Средняя | Chunk-based diff; показывать diff по разделам |

## Dependencies
- Фаза 1 (генерация)
- Фаза 5 (RAG-enhanced генерация) — опционально

# Фаза 7: Версионность документов

## Objective
Полноценное управление версиями: каждая итерация документа — новая версия с возможностью просмотра, скачивания, отката и привязки анализа к конкретной версии.

## Business Value
Юридическая значимость: важно знать, какая версия документа была утверждена в какой момент. Аудит, архивирование, ссылки на актуальную редакцию.

## Scope

### Backend
1. **Таблица `DocumentVersion`:**
   - id, document_id, version_number, file_path, file_hash, file_size, author_id, comment, created_at
   - При создании: version = max(existing) + 1
   - При утверждении: фиксация версии (approved_version_id в Document)

2. **Привязка анализа к версии:**
   - `DocumentAnalysis`: document_version_id (FK)
   - При переключении между версиями: отображение анализа именно той версии

3. **API Endpoints:**
   - `POST /api/v1/documents/{id}/versions` — создать новую версию (загрузить файл)
   - `GET /api/v1/documents/{id}/versions` — список версий
   - `GET /api/v1/documents/{id}/versions/{v}` — скачать версию
   - `POST /api/v1/documents/{id}/versions/{v}/restore` — сделать версию текущей (копирование в новую версию)
   - `GET /api/v1/documents/{id}/versions/{v1}/diff/{v2}` — diff между версиями

4. **Миграция данных:**
   - Существующие документы (без версий) получают version=1 автоматически

### Frontend
1. **Вкладка «Версии» на DocumentDetailPage:**
   - Таблица: Версия (v1, v2), Дата, Размер, Кем создана, Комментарий, Действия
   - Действия: Скачать, Сравнить (чекбоксы для выбора двух версий → показать diff)
   - Маркер: текущая версия (highlight)
   - Кнопка «Восстановить эту версию» (с подтверждением)

## Acceptance Criteria
1. При загрузке нового файла создаётся новая версия (v2, v3...)
2. Можно скачать любую версию
3. Можно сравнить две версии (diff)
4. При восстановлении версии создаётся новая версия с контентом выбранной
5. Анализ привязан к версии (переключил версию — видишь анализ этой версии)
6. История версий сохраняется при любых изменениях

## Risks
| Риск | Вероятность | Митигация |
|------|------------|-----------|
| Много версий → рост хранилища | Средняя | Архивация старых версий; возможность удаления (cascade check) |
| Восстановление случайно выбрано | Низкая | Подтверждение: «Вы уверены? Будет создана новая версия» |

## Dependencies
- Фаза 3 (документооборот, статусы)
- Фаза 4 (анализ при approved)
- Фаза 6 (корректировка по правкам)

## Технические решения (общие для всех фаз)

### LLM Abstraction (единый интерфейс)
```python
class LLMClient(ABC):
    @abstractmethod
    async def generate(
        self,
        prompt: str,
        system_prompt: str = "",
        temperature: float = 0.3,
        max_tokens: int = 16384,
        stream: bool = False,
    ) -> str | AsyncGenerator[str, None]:
        ...
```

### Статусная модель (единая)
```
DRAFT     → REVIEW, ARCHIVED
REVIEW    → DRAFT, APPROVED, ARCHIVED
APPROVED  → CANCELLED, ARCHIVED
CANCELLED → DRAFT, ARCHIVED
ARCHIVED  → (терминальный)

Администратор (admin) может перевести документ в любой статус
без ограничений матрицы переходов.
```

### Событийная модель
- Статус `approved` → триггер анализа (Фаза 4)
- Создание версии → триггер обновления метаданных
- Изменение документа → триггер обновления vector store

### Хранение
- **Файлы:** локальная папка `storage/{holding_id}/{document_id}/v{version}/`
- **Метаданные:** PostgreSQL → SQLAlchemy
- **Векторы:** ChromaDB (коллекция на холдинг)
- **Временные файлы:** `storage/temp/` (автоочистка)

### Безопасность
- JWT токены (access + refresh)
- Все эндпоинты проверяют принадлежность к холдингу пользователя
- Роли: admin (полный доступ), editor (создание/редактирование/статусы), member (legacy = editor), viewer (только чтение)
- Доступ к файлам: только через API (прямой доступ к папке запрещён)
